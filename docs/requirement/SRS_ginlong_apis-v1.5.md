## 4. 系统范围与边界

### 4.1 系统上下文

本范围关注 Solis WMS 与 Odoo 之间的 Ginlong API 业务边界：按各接口方向接收 Solis 请求，或由 Odoo 按已确认契约回传/提供仓库事件及库存信息。项目负责人提供的 Ginlong 接口矩阵将 API03 列为 Ginlong → Odoo；该方向作为当前本地开发契约，实际网络联调仍需在 CC-GIN-006 验证。

V3.1 资料把对端称为“第三方 WMS”；本项目按 A-001 将该角色映射为 BeeSmart Odoo。该映射沿用 SRS v1.0 已冻结的系统边界，不表示 Ginlong 已对其他接口细节作出确认。

### 4.2 本范围内

- 接收和发送 Ginlong API 数据，并将 API 数据与 Odoo 现有业务服务及业务记录集成。
- 接收入库单、待出库单、盘点单和物料档案等 Solis 数据，调用现有 Odoo 业务服务完成处理。
- 接收库存查询请求，并调用现有 Odoo 库存服务构造查询响应。
- 通过用户在 Odoo 业务单据上的操作，准备收货确认、入库完成、备货完成、发货完成和盘点完成 Payload，并调用对应 Ginlong 接口。
- 记录请求接收、业务处理及结果回传的独立状态和可追踪结果。
- 记录每次手动回传操作，支持按已确认接口契约进行失败重试。
- 对已确认的接口字段、Payload 规则和数据映射进行开发及本地模拟测试；仅将依赖尚未取得的 Ginlong 外部资料的部分列为待办。

### 4.3 本范围外

- 重复实现 Odoo 现有 WMS 的入库、出库、盘点、库存、拣选、发货及主数据业务逻辑；本模块集成并调用现有 Odoo 业务服务。
- Karl Rapp 的 XML 文件解析/生成、VPN、FTP 和 KR Gateway 的部署与接口实现；这些工作属于后续 `karlrapp_gateway` 范围。
- Karl Rapp WMS 的内部作业处理和其可提供的作业事件能力。
- Solis WMS 内部的 SAP 过账实现。
- 未经双方确认的额外业务接口、字段和状态。

## 6. 业务需求

### 6.1 业务规则

1. 收货确认和入库完成是两个不同业务节点，系统不得将一个节点自动解释为另一个节点。
2. 备货完成和实际发货完成是两个不同业务节点，系统不得将备货完成直接视为实际发货完成。
3. **请求接收、Odoo 业务处理和结果回传是三个不同状态。** 收到请求只表示 Odoo 已接收，不代表业务处理完成；业务处理完成也不代表 Ginlong 已接收回传结果。
4. V3.1 指出待入库单、待出库单和盘点单的修改采用删除后新增的处理方式。`ginlong_apis` 应调用现有 Odoo 业务服务处理相应操作，不在集成层重复实现 WMS 业务状态和库存规则。
5. 02、04、06、08、10 接口的每次回传（包括失败后的重试）均由用户在对应 Odoo 业务单据上手动点击按钮触发。不得因单据状态变化、定时任务、后台重试或其他自动化流程自动发起回传。
6. 对 02/04/06/08/10 回传，本期仅执行权限、安全、数据完整性和格式校验，不执行未在本条列明的业务状态拦截或其他额外业务检查。新增业务检查条件必须通过需求变更追加并批准；不属于本 SRS 已冻结或本次拟更新的基线，也不阻塞本次评审。
7. 每次手动回传都应单独记录操作及结果。失败应支持用户再次点击按钮发起重试；重复回传及结果未知时的处理按已确认契约执行，未确认的规则列为待决事项。
8. 对重复请求、部分处理、删除/撤销及失败情况保留可核对结果；不得由集成层假设未确认的业务键、批次完成语义或库存处理规则。
9. Ginlong 产品按 `productCode` 建立产品模板；不同 `owner` 使用该模板下各自的产品变体。产品主数据的共享属性由模板统一维护，同一 `productCode` 的共享属性必须一致，不同货主不得形成相互冲突的模板值。
10. API07 的模板共享属性包括产品名称、规格型号、单位、功率、国家标准、认证型号、产品形态、重量及尺寸；货主和 owner 维度的产品识别属于变体。API07 收到共享字段冲突时应拒绝该请求且不得修改既有产品。
11. API07 只接受客户确认的 `原材料`、`半成品`、`成品` 三种 `productForm`；原材料不要求 SN，半成品和成品要求 SN；其他值拒绝且不修改既有产品。依据见 [TV productForm OI 关闭补充 v1.1](../context/report/TV_ginlong_product_variants_api07_sn_OI-closure-v1.1.md)。V3.2 工作簿未列出该枚举；本项目规则由客户明确确认，不将其误述为 V3.2 文档原文。
12. API01 若货主编码在现有 `res.partner.ginlong_owner_code` 中不存在，应创建货主档案并关联入库单；已存在则复用。API03 不自动创建货主或产品，须按订单货主和每条 `productCode` 的组合找到已有产品，否则拒绝整单。
13. API09 的 `quantity` 表示 Odoo 当前库存记录中的实际物理在库数量，不扣除预留量。库存按货主、仓库和产品编码区分；查询不得导致库存移动或调整。
14. API01 Add 的客户预报 SN 规则仅适用于 `businessType` 精确等于「保税_海外收货入库」的请求。此类型下，SN 管理产品必须提供完整 `snList`，每条真实 SN 的 `quantity=1`，同一请求内同一产品不得重复 SN；非 SN 管理原材料可省略 `snList`，若提供则 `productSN=productCode`，数量表示托盘上的预报数量，同一原材料可在不同托盘行重复出现。同一产品可分布在多个托盘，同一托盘可包含多个产品；对提供分配行的产品，其 `snList.quantity` 按产品汇总必须等于 `details.quantity`。校验须在写入业务 Order 前完成；任一行失败时拒绝整单，不得留下部分 Order 或成功幂等结果。非该 `businessType` 时，API01 Add 业务处理忽略 `snList`，不校验也不保存到 Order。此规则不改变 API 日志记录原始请求的既有行为。
15. API01 保存的 `snList` 和 `palletCode` 是客户预报，不代表实际 SN、托盘或库存；API01 不创建 Lot、package、Picking、stock move 或库存。实际收货事实独立保存在实际 `stock.picking` / `stock.move.line`；API04 只依据实际收货记录生成回传数据，不以 API01 预报替代。本次不实现预报与实收的自动比较、差异展示或差异处置。


16. **API01/03/05/07 Add 有效性规则（项目负责人 2026-11-24 确认）**：API01 的全局业务键为 `inboundOrderNo`，API03 为 `outboundOrderNo`，API05 为 `countOrderNo`，均不含 `project`；三个模型中 `state != cancel` 的记录有效，`state=cancel` 无效。全局判重不改变现有 project 归属和访问权限；新订单仍属于 API User 对应的 project，Delete 仍按原权限范围定位单据。API07 按 `(owner, productCode)` 定位 `product.product` 变体；`active=True` 有效，`active=False`（归档）无效。存在有效记录时 Add 必须拒绝，不论新旧 Payload 是否相同；不存在有效记录时进入原有校验和创建流程。历史成功幂等记录不得阻断取消/归档后的新 Add，也不得作为新请求成功结果重放。取消/归档只使旧记录失效，不物理删除历史业务数据或幂等审计。并发 Add 必须保证同一有效键至多一条有效记录。此规则取代 IHR-GIN-005 IHR-009（2026-11-22）中 API01 删除后仍禁止同单号重加的旧决定；旧 IHR/ATR/HVR 保留为历史证据。API07 仍无 Ginlong Delete。
17. **API01/03/05 操作有效性（项目负责人 Human Review 补充，2026-11-24）**：Add 按第 16 条判定有效业务键；实现支持的 Edit 和 Del 必须先定位当前有效业务记录。Edit/Del 的记录范围继续遵循当前 API User 的 project 权限。Del 仅取消有效记录；如果不存在有效记录（包括仅有 `state=cancel` 的历史记录），返回业务错误，不得重放历史成功 Del 响应。该错误判断不依赖请求 Payload 是否与历史请求相同或不同。已取消的记录、历史幂等行和 API 日志完整保留。API01 的 Ginlong Action 契约仍只按 V3.2 支持 Add/Del，本补充不增加 API01 对外 Edit Action。

### 6.2 功能需求

**主动回传职责原则（适用于 API02/04/06/08/10）：** 业务模块负责产生和记录业务事实，API 模块负责读取、转换、传输业务事实并记录回传结果。不得为了 API 回传要求用户重复维护已有业务数据。业务操作日志、Ginlong API Event 与 API Log 各自记录业务动作、事件幂等和 HTTP 尝试/结果，不互相替代。

方向基于 V3.1 与项目负责人提供的 Ginlong 接口矩阵；API03 方向按 Ginlong → Odoo 处理。详细字段见来源工作簿的接口逻辑和“对接字段”工作表；矩阵方向确认不表示已完成真实网络联调。

| --- | --- | --- | --- |

### 6.3 异常与人工恢复需求

1. 系统应分别记录请求接收结果、Odoo 业务处理结果，以及适用时的 Ginlong 回传/确认结果。前一阶段成功不得自动视为后一阶段成功；状态名称、转换及对外响应表达由 TV/TDD 根据最终契约定义。
2. 请求缺少必需数据、数据格式不符合已确认字段契约、请求未通过安全或权限校验时，系统应拒绝处理或回传，并记录可追踪原因。其他业务校验由现有 Odoo 业务服务和已确认业务规则负责；本 SRS 不新增业务状态拦截条件。
3. 失败或结果未知的请求/回传应保留与接口编号、业务单号或事件标识、操作人（适用时）及处理时间的关联，供授权人员查看和恢复。
4. 对 02/04/06/08/10，每次手动回传应记录一次操作、Payload/关联信息及结果；失败应支持用户再次点击对应按钮重试，后台不得自动重试。重复回传、幂等键、未知结果的核实与重试策略按已确认契约执行；未定义部分列为待决事项，不由本 SRS 预设。
5. 请求接收、业务处理及回传采用同步还是异步模式待决；无论最终模式如何，均应能区分并追踪上述阶段的结果。
6. V3.1 提到接口异常时部分流程可采用 Excel 导入/导出。本能力不属于本 SRS 范围；如业务方后续要求纳入，须通过需求变更评审其范围、模板和人工审核流程。

### 7.2 数据保留与审计

- 每个请求/回传结果应能追溯至来源系统、接口编号、业务单号或事件标识及处理时间。
- 复用现有 `worlddepot` API 日志能力记录 Ginlong 接收请求及其处理结果；02/04/06/08/10 的每次用户触发、重试和回传结果也须记录，并能关联接口编号、业务单据和操作人。若现有日志字段不足，应在现有日志能力上扩展，不另建平行日志体系。
- API Secret、Access Token、Authorization Token、签名密钥等认证凭据不得写入 API/应用日志。业务 Payload 不作整体脱敏；仅对经数据保护要求认定须保护的个人或敏感字段按批准规则遮蔽或限制访问，并保留排障、审计所需的业务数据。
- API01 在非保税业务类型下即使忽略 `snList` 的业务处理，现有 API 日志仍保留收到的原始请求报文；日志留存不表示该字段已进入 Order 或被业务校验接受。
- 原始报文、处理结果和错误信息的保存范围及期限待双方数据治理要求确认。

## 10. 验收范围

验收分为本地模拟验收和真实环境联调验收。已确认的接口契约可先按本地模拟场景开发和验收；缺失外部资料只阻塞依赖该资料的部分。具体协议断言和 Ginlong 侧预期结果须在正式接口文档确认后补全。

**本地模拟验收（不依赖 Ginlong 实际环境）：**

1. 覆盖 01–10 已确认的字段来源、字段映射和数据准备；对尚未确认的字段规则使用模拟契约，不将其作为最终外部契约。
2. 验证 01/03/05/07/09 请求由集成入口接收，并调用 Odoo 现有业务服务或库存服务；业务和库存作业规则不在集成层另行实现。
3. 验证 02/04/06/08/10 的每次回传（含重试）只能由用户点击对应 Odoo 业务单据按钮触发；按钮调用对应接口、生成 Payload 并记录操作及结果；状态变化、定时任务、后台重试或其他自动化不得触发回传。
4. 验证权限、安全、数据完整性和格式校验，并验证回传操作可追溯、失败可重试；重复回传和结果未知场景按已确认契约覆盖，未确认行为保持为待决，不作为本地验收的预设规则。
5. 分别验证请求接收、业务处理及结果回传状态，确保一个阶段成功不会被显示为其他阶段成功；同步/异步交互模式留待 TV/TDD 确认。

**真实环境联调验收（依赖 Ginlong 资料及测试环境）：**

6. 逐接口验证经批准的 URL、鉴权、请求/响应格式、错误码、超时和重试契约，以及 Ginlong 实际处理与确认结果。
7. 验证部分作业、重复回传、结果未知、取消/撤销等场景；仅按双方已确认的业务规则和契约判定通过条件。
8. 验证物料新增/修改和库存查询的关联字段、查询条件及数量口径符合双方确认结果。
9. 双方联调记录请求关联标识、预期结果和实际结果；正式验收由授权业务负责人签署。
