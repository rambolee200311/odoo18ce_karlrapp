# Ginlong–Odoo–Karl Rapp 三系统集成架构原则

| 项目 | 内容 |
|---|---|
| 版本 | v2.9 |
| 日期 | 2026-11-18 |
| 状态 | 项目用户确认的架构认知 |
| 适用范围 | `ginlong_apis`、`karlrapp_gateway`、现有 Odoo WMS 及三系统集成开发 |

## 1. 总体架构

采用 **Ginlong 下达业务指令、Karl Rapp 执行现场作业、Odoo 管理业务订单并记录实际执行结果** 的架构。

```text
Ginlong (Solis)
    │ 下达业务指令：入库、出库、盘点、产品等
    ▼
Odoo
    │ 接收和管理业务订单
    ▼
Karl Rapp Gateway
    │ 通过 VPN / FTP 交换文件；XML 与 JSON 格式转换
    ▼
Karl Rapp WMS
    │ 执行实际仓库作业
    ▼
Karl Rapp Gateway
    │ 返回实际执行数据
    ▼
Odoo
    │ 使用 stock.picking 记录实际执行结果
    │ 通过 Odoo 原生库存机制反映实际库存移动
    ▼
Ginlong (Solis)
    接收执行结果；按约定查询库存
```

核心原则：**Ginlong 是业务指令来源，Karl Rapp 是仓库现场执行方，Odoo 是业务记录、库存管理与三方数据交换中心。** Gateway 是通信和格式转换组件，不是独立业务系统。

## 2. 系统职责

### 2.1 Ginlong / Solis

- 下达入库、出库、盘点等业务指令并提供产品主数据。
- 按接口约定查询库存。
- 接收 Odoo 回传的仓库执行结果。
- 不直接操作 Odoo 库存，也不直接控制 Karl Rapp WMS。

### 2.2 Odoo

- 接收和处理 Ginlong 业务指令，使用现有 WMS Order 模型管理业务要求。
- 通过 `karlrapp_gateway` 向 Karl Rapp 传递业务数据，并接收其实际执行结果。
- 使用现有 `stock.picking` 记录 Karl Rapp 返回的实际收货、发货等结果；由 Odoo 原生库存机制反映真实库存移动。
- 依 Ginlong 接口约定提供库存查询，并按约定回传执行结果。
- 不负责仓库现场收货、上架、拣货、发货或扫码操作。

### 2.3 Karl Rapp

- 通过自身 WMS 执行收货、上架、拣货、发货、盘点等现场作业。
- 是现场作业结果及其实际数量等执行数据的来源，并将结果返回 Odoo。

### 2.4 `karlrapp_gateway`

- 通过 VPN、FTP 与 Karl Rapp 交换文件。
- 安全解析/生成 XML，并负责 XML 与 JSON 的格式转换和必要的文件安全、大小、格式、完整性检查。
- 向 Odoo 交付转换后的执行数据，避免 Karl Rapp 原始 XML 直接进入 Odoo 业务处理层。
- 不管理业务订单、不计算库存、不作业务决策、不建立独立业务模型。

## 3. Odoo 数据与执行原则

### 3.1 优先复用现有模型

优先使用现有 Order、`stock.picking`、`stock.move`、`stock.move.line` 及 Odoo 原生库存模型。不得因三方集成重复建立订单、库存台账、托盘台账或执行记录模型。若经实际验证发现现有模型无法记录批准的需求，应先完成对应的需求/技术设计和 Coding Contract 变更，再作最小扩展。

### 3.2 Order 与 `stock.picking` 松耦合

- Order 记录 Ginlong 下达的业务指令和要求。
- `stock.picking` 记录 Karl Rapp 实际执行并返回 Odoo 的仓库结果。
- 两者不要求建立强制外键；可按现有订单 ID/编码等业务标识进行匹配，并结合产品、批次、数量、托盘等实际数据交叉核对。
- 允许一张业务订单对应多次实际仓库执行；逐次保存实际执行记录，并按业务标识汇总核对。
- 不因 Ginlong 指令数量推定仓库作业已完成，也不强制一张 Order 只能对应一张 `stock.picking`。

### 3.3 库存以实际执行为准

只有 Karl Rapp 返回的实际执行结果进入 Odoo 后，Odoo 才能按现有业务流程处理相应 `stock.picking` 和库存移动。不得仅凭 Ginlong 的指令创建库存结果，不得在 `ginlong_apis` 或 Gateway 中复制库存计算/扣增逻辑。

`ginlong_apis` 不独立执行或处理仓库收货、发货。实际出入库作业数据来自 Karl Rapp；Odoo 依据返回结果使用 `stock.picking` 和原生库存机制记录实际移动。Ginlong API09 返回 Odoo 当前的**实际物理在库数量**，按 `(ownerCode, warehouse, productCode)` 区分；使用 Odoo 当前实存量，不以 `quantity - reserved_quantity` 计算可用量，也不以 Ginlong 指令数量或计划数量推算库存。

### 3.4 分批及重复数据

- 允许一张业务订单多批次执行，各批次实际结果分别记录并可核对。
- 同一实际执行结果重复传输不得造成重复收货、重复发货或重复库存移动；优先复用现有业务标识和 Odoo 业务能力保障幂等。
- 重复判定键、冲突处理和对外响应遵循经批准的接口/业务契约；未确认时列为待决，不自行补造规则。

### 3.5 执行数据核对

可以对业务指令与 Karl Rapp 实际执行数据进行一致性核对，例如订单编号、产品、数量、批次和托盘。发现差异时记录并反馈，按现有业务流程处理；不因此增加强制外键、额外审批或未经批准的业务状态拦截。

### 3.6 托盘生命周期

托盘生命周期是项目必须保留的业务需求。应能沿稳定托盘标识核对收货、库内移动/拆装、出库等实际事件及相关产品、数量、时间、位置和单据。先验证现有 Package 与库存移动记录是否已覆盖；不得默认新建重复台账，也不得为追踪托盘绕开现有 WMS 库存流程。盘点接口的独立盘点数据不得被混同为库存调整。

## 4. 三个项目模块的边界

| 模块 / 系统 | 职责 |
|---|---|
| `ginlong_apis` | Ginlong ↔ Odoo REST API 数据交换；复用 Odoo 认证、权限、日志和业务模型 |
| `karlrapp_gateway` | Odoo ↔ Karl Rapp 文件通信、XML/JSON 转换及必要的文件安全/完整性检查 |
| 现有 Odoo WMS | Order、实际 `stock.picking`、库存移动、库存及相关业务记录；现场作业仍由 Karl Rapp 执行 |

三个部分职责清楚、通信与业务分离；Odoo 业务逻辑集中在现有 WMS 能力中，不在 Gateway 或 Ginlong 模块中重复开发。

## 5. Ginlong ↔ Odoo 接口原则

- 按 Ginlong 已确认的 RESTful API 契约交换数据。
- Odoo 用户手动触发的回传继续使用相应业务单据上的按钮；不得擅自变成自动回传。
- Ginlong 协议或业务规则尚未确认的部分保持待决，不以示例自行推定为正式契约。
- API 认证、Token、权限和 API 日志优先复用 `worlddepot` 现有能力；凭据不得明文写入日志。

### 5.1 五个回调接口的业务事件与模拟数据来源

五个回调接口都由用户在相应 Odoo 业务 Order 上手动点击触发；按钮触发点相同，但业务事件和 Payload 数据来源不同。以下对应关系是开发时必须遵循的项目认知，本地模拟应从所列业务对象准备数据，不得把订单要求、备货结果、仓库实际执行结果和盘点结果混为一类。

| 回调 API | 业务事件 | 本地模拟数据来源 |
|---|---|---|
| API02 | 收货确认 | inbound.order 收货数据 |
| API04 | 入库完成 | stock.picking 入库完成数据 |
| API06 | 备货完成 | outbound.order 备货完成数据 |
| API08 | 发货完成 | 出库 Order 上已保存的实际发货明细及状态 |
| API10 | 盘点完成 | count.order 独立盘点任务及其采集结果 |

- API02 与 API04 表达不同业务事件：前者取入库 Order 的收货数据，后者取实际入库完成的 stock.picking 数据。
- API06 与 API08 表达不同业务事件：前者取出库 Order 关联的实际备货数据，后者取出库 Order 上已保存的实际发货明细及状态。
- API10 使用独立盘点任务和采集结果；不得把它当成库存调整，也不得以 stock.quant 数量替代盘点结果。
- API04/API08 的实际执行数据与 Order 仍按业务数据核对，不要求建立强制外键。多次执行如何选择、汇总及映射到 Ginlong 报文，必须依据已批准的接口契约；未确认时列为待决，不自行推断。
- 以上是本地模拟的数据来源原则，不替代 Ginlong 尚未确认的字段、协议和业务规则。若其与已批准 SRS/TDD 的具体定义存在差异，先指出差异并完成相应上游变更，再实施受影响接口。

### 5.1.1 已确认的回传数据记录规则

- API02：入库 Order 维护持久化实际收货明细，记录关联的实际产品、数量、SN/托盘及收货状态；不实现入库 Order 取消控制及取消回传。
- API06：从实际备货 `stock.move.line` 读取产品、SN、数量和托盘；`palletQty` 默认对实际 `package_id` 去重计数，可保存人工覆盖。重量按产品档案单件重量乘实际备货数量；毛重默认等于净重并允许人工修改。
- API08：出库 Order 维护持久化实际发货明细，记录关联的实际产品、数量、SN/托盘及发货状态；不实现出库 Order 取消控制及取消回传。
- API02/API08：明细状态一致时按已保存状态生成订单级确认字段；同一订单的明细同时出现 Y 与 N 时不发送，提示并记录失败。
- API06：`palletQty` 和 `totalWeight` 按 DECIMAL(18,6) 字段对应的 V3.2 字符串样例序列化为 JSON string，最多六位小数。单件重量来源是 API07 映射的 `product.ginlong_weight`；按实际备货数量计算，毛重默认净重并允许保存人工值覆盖。
- 其他协议或字段存在歧义时列出具体问题，不自行补造值域、汇总口径或序列化规则。
- API07 的产品识别键为 `owner + productCode`。允许不同 owner 使用相同 `default_code`；不建立 Ginlong 产品映射模型。所有受影响的 WMS 查询需按现有货主关联消歧，重复码无法唯一定位时返回明确歧义，不得用 `limit=1` 任意选取。

### 5.3 Odoo 视图交互：Wizard 与标准 Form

必须按数据是否需要长期保存来选择界面形态，不以 `TransientModel` Wizard 代替持久化业务表单。

| 使用场景 | 推荐方式 | 认知原则 |
|---|---|---|
| 从多个模型选择记录并建立一次性关联 | Wizard | 临时数据，用完即弃 |
| 批量选择多条记录执行一次操作 | Wizard | 只收集 Action 参数，不保存业务中间状态 |
| 一次性确认或选择操作参数 | Wizard | 不需要持久化追溯时使用 |
| 录入并长期保存业务数据 | 标准 Form | 使用持久化 ORM 模型，支持追溯 |
| 分阶段填写、修改或补充业务明细 | 标准 Form | 可随时保存，之后再次打开继续修改 |
| 失败后核对、修改并重试 | 标准 Form | 按钮从已保存 ORM 记录读取数据；不依赖未保存的前端状态 |

对 Ginlong 回传而言，五个回传按钮应优先在现有业务 Form 增加「Ginlong 回传数据」Notebook 页面。确需补充的值保存到现有模型的最小字段或明细上；发送按钮只读取已保存数据。失败后用户可编辑并再次发送，每次发送新建一条现有 API 日志记录，不能覆写历史日志。业务用户不查看或编辑 JSON。

### 5.2 入站业务唯一键与保护要求

以下 Ginlong 入站业务唯一键由项目用户明确确认，后续设计和实现不得自行替换：

| 接口 | 业务唯一键 |
|---|---|
| API01 | `inboundOrderNo`（入库单号） |
| API03 | `outboundOrderNo`（出库单号） |
| API05 | `countOrderNo`（盘点单号） |
| API07 | `owner` + `productCode`（货主 + 产品编码） |

后续 Ginlong 接口矩阵确认 API03 出库单创建方向为 Ginlong → Odoo，Object ID 为 `TPL_Pending_Delivery_Note`，接口路径为 `/api/ginlong/TPL_Pending_Delivery_Note`。CC-GIN-003 早期 A-003 方向假设已由该资料取代；真实 Ginlong 联调仍须单独授权并执行。

入站接口需按 API、业务键和规范化请求内容指纹识别完全重复请求；这也是请求级防抖边界：完全相同且已成功的请求可复用原结果，处理中不得重复执行业务。请求内容不同即使业务键相同，也必须交由该接口经批准的新增、修改或删除规则处理，不能仅凭业务键判为重复。API07 的产品识别键必须同时包含 Ginlong 货主与产品编码；这不要求另建一套产品档案。

Ginlong 入站 API 按 API 和已认证调用方分别限流，四个 API 独立计数、阈值可单独配置：API01/03/05 默认每秒 10 次，API07 默认每秒 100 次。调用方身份使用 `worlddepot` Token 验证后取得的 API 用户身份，不信任客户端 IP 转发头。限流状态须存于 PostgreSQL 并经 Odoo ORM 原子更新，确保多 Worker/进程共享；禁止进程内变量、缓存或 Redis。采用 UTC 固定一秒窗口，不使用滚动窗口或令牌桶；超限返回 HTTP 429 与 `Retry-After`。此处记录已确认要求，不授权编码。

Ginlong 入站 UPDATE 复用对应现有 WMS 业务模型的修改逻辑；`audit_log` 现有字段变更跟踪继续按其配置工作，本项目不为此另建跟踪机制。订单类 DELETE（API01/03/05）只把对应订单状态置为 `cancel`，不物理删除订单或相关原始业务数据；重复删除已取消订单应幂等成功。API07 是产品档案接口，不套用订单取消规则；其 DELETE 行为须以 Ginlong 已确认契约为依据，当前不推定物理删除或停用。

#### 货主编码、产品编码与库存识别

- Ginlong 传输的货主标识是**货主编码**，不是货主名称。接口映射、检索和库存归属均使用编码，不以伙伴显示名称或其他可变名称代替。
- Ginlong 推送的入库单和出库单均为**单货主单据**。订单级 `ownerCode` 适用于该单据的全部产品明细；一张单据不混合多个货主。
- 不同货主可以拥有相同 `productCode`。Ginlong 产品身份键为 `(ownerCode, productCode)`；`productCode` 单字段不能唯一识别 Ginlong 产品，也不得据此跨货主合并产品或库存。
- API01 入库订单收到 owner 编码后，按 `res.partner.ginlong_owner_code` 查找货主；存在则复用，不存在则创建货主档案，并关联到入库订单；后续相同编码复用同一档案。
- API03 出库订单必须先以表头 owner 编码找到已有货主，再逐行以 `owner + productCode` 查找现有产品。货主或产品组合不存在时拒绝订单并记录业务错误；API03 不自动创建产品，产品档案由 API07 维护。
- 产品身份按 `(ownerCode, productCode)` 区分；实际库存按 `(ownerCode, warehouseCode, productCode)` 区分。API09 查询指定货主与仓库的库存，再按产品编码返回；相同产品编码在不同货主或仓库下必须分别归属和计算，不得合并。
- Ginlong 产品身份仍按 `product.product.ginlong_owner_code + default_code` 区分。API09 的库存货主归属则使用 `owner` 查找 `res.partner.ginlong_owner_code`，再按 `stock.quant.owner_id` 隔离库存；不以 Contact Name 或产品编码单字段代替货主，也不新增货主映射模型。
- API09 的仓库请求值是编码，不能以 `stock.warehouse.name` 显示名称匹配。现有 `stock.warehouse.code` 是短码字段（长度 5）；实现按其精确匹配，未知编码拒绝查询，不把任意编码映射到唯一仓库。Ginlong 的 `warehouse` 字段允许 40 字符，外部编码与 Odoo 短码是否相同尚无确认；在确认/所需字段调整前，不能声称已兼容任意 Ginlong 仓库编码。无需另建映射表。
- API09 按匹配的仓库内部库位及 `stock.quant.owner_id` 返回该货主的完整产品列表；没有该 owner 的库存时返回空 `inventoryList`，不能泄露其他货主或仓库库存。
- API09 只读，不扣减预留量、不生成库存移动或调整。当前开发库没有真实内部库存记录；模拟库存自动化只能验证查询与隔离行为，不能视作 Karl Rapp 到 Odoo 的库存同步证据。
- Ginlong 管理界面复用现有 Settings、`world.depot.api.log` 和 WMS 业务模型。回传日志通过单一 Reference 字段定位原业务单据，库存管理员只读访问；失败后用户返回原单据使用既有按钮，不建立独立重发流程。

## 6. 安全与开发约束

1. Gateway 对外部文件/XML 做必要安全解析，并限制文件大小、格式及结构。
2. Odoo 负责业务数据处理及必要的数据完整性/库存一致性保障；具体拦截规则须来自批准的需求和业务契约。
3. 不新增无必要的中间件、日志模型、通用集成框架、业务状态或审批门禁。
4. 本项目不使用、不安装、不启用 `stock_barcode`。
5. 开发和测试期间，所有数据库操作仅允许通过 `odoo shell -c odoo.conf` 使用 Odoo ORM；禁止直接访问 PostgreSQL、`psql`、数据库驱动或执行 SQL。
