| 项目 | 内容 |
|---|---|
| 版本 | v1.1 |
| 日期 | 2026-11-17 |
| 状态 | 项目用户确认的架构认知 |
| 适用范围 | `ginlong_apis`、`karlrapp_gateway`、现有 Odoo WMS 及三系统集成开发 |

## 1. 总体架构

采用 **Ginlong 下达业务指令、Karl Rapp 执行现场作业、Odoo 管理业务订单并记录实际执行结果** 的架构。

```text
Ginlong (Solis)
    │ 下达业务指令：入库、出库、盘点、产品等
    ▼
Odoo
    │ 接收和管理业务订单
    ▼
Karl Rapp Gateway
    │ 通过 VPN / FTP 交换文件；XML 与 JSON 格式转换
    ▼
Karl Rapp WMS
    │ 执行实际仓库作业
    ▼
Karl Rapp Gateway
    │ 返回实际执行数据
    ▼
Odoo
    │ 使用 stock.picking 记录实际执行结果
    │ 通过 Odoo 原生库存机制反映实际库存移动
    ▼
Ginlong (Solis)
    接收执行结果；按约定查询库存
```

核心原则：**Ginlong 是业务指令来源，Karl Rapp 是仓库现场执行方，Odoo 是业务记录、库存管理与三方数据交换中心。** Gateway 是通信和格式转换组件，不是独立业务系统。

## 2. 系统职责

### 2.1 Ginlong / Solis

- 下达入库、出库、盘点等业务指令并提供产品主数据。
- 按接口约定查询库存。
- 接收 Odoo 回传的仓库执行结果。
- 不直接操作 Odoo 库存，也不直接控制 Karl Rapp WMS。

### 2.2 Odoo

- 接收和处理 Ginlong 业务指令，使用现有 WMS Order 模型管理业务要求。
- 通过 `karlrapp_gateway` 向 Karl Rapp 传递业务数据，并接收其实际执行结果。
- 使用现有 `stock.picking` 记录 Karl Rapp 返回的实际收货、发货等结果；由 Odoo 原生库存机制反映真实库存移动。
- 依 Ginlong 接口约定提供库存查询，并按约定回传执行结果。
- 不负责仓库现场收货、上架、拣货、发货或扫码操作。

### 2.3 Karl Rapp

- 通过自身 WMS 执行收货、上架、拣货、发货、盘点等现场作业。
- 是现场作业结果及其实际数量等执行数据的来源，并将结果返回 Odoo。

### 2.4 `karlrapp_gateway`

- 通过 VPN、FTP 与 Karl Rapp 交换文件。
- 安全解析/生成 XML，并负责 XML 与 JSON 的格式转换和必要的文件安全、大小、格式、完整性检查。
- 向 Odoo 交付转换后的执行数据，避免 Karl Rapp 原始 XML 直接进入 Odoo 业务处理层。
- 不管理业务订单、不计算库存、不作业务决策、不建立独立业务模型。

## 3. Odoo 数据与执行原则

### 3.1 优先复用现有模型

优先使用现有 Order、`stock.picking`、`stock.move`、`stock.move.line` 及 Odoo 原生库存模型。不得因三方集成重复建立订单、库存台账、托盘台账或执行记录模型。若经实际验证发现现有模型无法记录批准的需求，应先完成对应的需求/技术设计和 Coding Contract 变更，再作最小扩展。

### 3.2 Order 与 `stock.picking` 松耦合

- Order 记录 Ginlong 下达的业务指令和要求。
- `stock.picking` 记录 Karl Rapp 实际执行并返回 Odoo 的仓库结果。
- 两者不要求建立强制外键；可按现有订单 ID/编码等业务标识进行匹配，并结合产品、批次、数量、托盘等实际数据交叉核对。
- 允许一张业务订单对应多次实际仓库执行；逐次保存实际执行记录，并按业务标识汇总核对。
- 不因 Ginlong 指令数量推定仓库作业已完成，也不强制一张 Order 只能对应一张 `stock.picking`。

### 3.3 库存以实际执行为准

只有 Karl Rapp 返回的实际执行结果进入 Odoo 后，Odoo 才能按现有业务流程处理相应 `stock.picking` 和库存移动。不得仅凭 Ginlong 的指令创建库存结果，不得在 `ginlong_apis` 或 Gateway 中复制库存计算/扣增逻辑。

### 3.4 分批及重复数据

- 允许一张业务订单多批次执行，各批次实际结果分别记录并可核对。
- 同一实际执行结果重复传输不得造成重复收货、重复发货或重复库存移动；优先复用现有业务标识和 Odoo 业务能力保障幂等。
- 重复判定键、冲突处理和对外响应遵循经批准的接口/业务契约；未确认时列为待决，不自行补造规则。

### 3.5 执行数据核对

可以对业务指令与 Karl Rapp 实际执行数据进行一致性核对，例如订单编号、产品、数量、批次和托盘。发现差异时记录并反馈，按现有业务流程处理；不因此增加强制外键、额外审批或未经批准的业务状态拦截。

### 3.6 托盘生命周期

托盘生命周期是项目必须保留的业务需求。应能沿稳定托盘标识核对收货、库内移动/拆装、出库等实际事件及相关产品、数量、时间、位置和单据。先验证现有 Package 与库存移动记录是否已覆盖；不得默认新建重复台账，也不得为追踪托盘绕开现有 WMS 库存流程。盘点接口的独立盘点数据不得被混同为库存调整。

## 4. 三个项目模块的边界

| 模块 / 系统 | 职责 |
|---|---|
| `ginlong_apis` | Ginlong ↔ Odoo REST API 数据交换；复用 Odoo 认证、权限、日志和业务模型 |
| `karlrapp_gateway` | Odoo ↔ Karl Rapp 文件通信、XML/JSON 转换及必要的文件安全/完整性检查 |
| 现有 Odoo WMS | Order、实际 `stock.picking`、库存移动、库存及相关业务记录；现场作业仍由 Karl Rapp 执行 |

三个部分职责清楚、通信与业务分离；Odoo 业务逻辑集中在现有 WMS 能力中，不在 Gateway 或 Ginlong 模块中重复开发。

## 5. Ginlong ↔ Odoo 接口原则

- 按 Ginlong 已确认的 RESTful API 契约交换数据。
- Odoo 用户手动触发的回传继续使用相应业务单据上的按钮；不得擅自变成自动回传。
- Ginlong 协议或业务规则尚未确认的部分保持待决，不以示例自行推定为正式契约。
- API 认证、Token、权限和 API 日志优先复用 `worlddepot` 现有能力；凭据不得明文写入日志。

### 5.1 五个回调接口的业务事件与模拟数据来源

五个回调接口都由用户在相应 Odoo 业务 Order 上手动点击触发；按钮触发点相同，但业务事件和 Payload 数据来源不同。以下对应关系是开发时必须遵循的项目认知，本地模拟应从所列业务对象准备数据，不得把订单要求、备货结果、仓库实际执行结果和盘点结果混为一类。

| 回调 API | 业务事件 | 本地模拟数据来源 |
|---|---|---|
| API02 | 收货确认 | inbound.order 收货数据 |
| API04 | 入库完成 | stock.picking 入库完成数据 |
| API06 | 备货完成 | outbound.order 备货完成数据 |
| API08 | 发货完成 | stock.picking 实际离仓数据 |
| API10 | 盘点完成 | count.order 独立盘点任务及其采集结果 |

- API02 与 API04 表达不同业务事件：前者取入库 Order 的收货数据，后者取实际入库完成的 stock.picking 数据。
- API06 与 API08 表达不同业务事件：前者取出库 Order 的备货完成数据，后者取 stock.picking 的实际离仓数据。
- API10 使用独立盘点任务和采集结果；不得把它当成库存调整，也不得以 stock.quant 数量替代盘点结果。
- API04/API08 的实际执行数据与 Order 仍按业务数据核对，不要求建立强制外键。多次执行如何选择、汇总及映射到 Ginlong 报文，必须依据已批准的接口契约；未确认时列为待决，不自行推断。
- 以上是本地模拟的数据来源原则，不替代 Ginlong 尚未确认的字段、协议和业务规则。若其与已批准 SRS/TDD 的具体定义存在差异，先指出差异并完成相应上游变更，再实施受影响接口。

## 6. 安全与开发约束

1. Gateway 对外部文件/XML 做必要安全解析，并限制文件大小、格式及结构。
2. Odoo 负责业务数据处理及必要的数据完整性/库存一致性保障；具体拦截规则须来自批准的需求和业务契约。
3. 不新增无必要的中间件、日志模型、通用集成框架、业务状态或审批门禁。
4. 本项目不使用、不安装、不启用 `stock_barcode`。
5. 开发和测试期间，所有数据库操作仅允许通过 `odoo shell -c odoo.conf` 使用 Odoo ORM；禁止直接访问 PostgreSQL、`psql`、数据库驱动或执行 SQL。
