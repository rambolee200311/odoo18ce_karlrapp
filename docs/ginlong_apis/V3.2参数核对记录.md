## 4. 物料信息表观察

工作簿包含 13 个字段，与 API07 的字段集合一致；样表有 8 条产品记录：

- 样表货主值只有 `2110`；8 个 `productCode` 均不重复。该样本不能证明其他货主不存在相同产品编码。
- `unit` 样值为“个”“PCS”“套”“台”；`productForm` 有“原材料”“成品”。
- 接口字段表将 `power` 定义为字符串 `VARCHAR(40)`，物料表中的样值是文本“0”“110”“10”，与字符串字段相符。
- `weight` 和长宽高在物料表中也是文本数字（样表为“0”），而接口字段类型为 `DECIMAL(18,6)`。发送 API07 JSON 前应将这些数值字段转为 JSON number；文本“0”与空单元格仍需区分。

## 5. 与当前 Odoo 实现的关系

### 参数模型结论

不需要建立独立的 Ginlong“参数模型”或复制一套产品主档。HTTP JSON 参数属于接口契约和请求映射；继续按字段映射至现有入库/出库单据、独立盘点任务以及 `product.product`。现有 `worlddepot` API 日志承担请求记录。

已经增加在现有 Odoo 模型上的 Ginlong 来源字段属于字段映射，不等于第二套产品档案；API05 独立盘点任务是已批准业务对象，也不是参数模型。

### 需要解决的数据/键匹配事项

1. **单位档案已为调试创建：** 在现有开发库中为“个”“PCS”“套”“台”各创建一个 Odoo UoM，并各自使用独立类别及 1.0 基准精度。这样 API07 可精确匹配样表单位，且在没有换算依据时不会将不同单位互相换算。业务方确认正式换算规则后再调整。
2. **API07 唯一键需复核：** V3.2 说明 Ginlong 以 `owner + productCode` 为唯一键。样表只有一个 owner，无法验证跨货主同编码情形；当前 API07 实现按 Odoo `default_code` 查找后更新 `ginlong_owner_code`。若同一 `productCode` 可属于多个 owner，该查找可能更新错误产品。先确认真实数据是否存在跨货主重码；优先评估在现有 `product.product` 扩展字段上按 owner 与编码识别，不预先新建映射模型。
3. **数值转换及 0/空值：** `power` 可按字符串保留；`weight`/尺寸需从导入表的文本数字转换为 Odoo Float / API JSON number。当前样表中的 0 作为明确值保留，空单元格映射为空值。
