## 1. 目的与职责边界

Ginlong 下达业务指令，Odoo 接收订单并转发给 Karl Rapp，Karl Rapp 执行仓库作业，Odoo 根据返回结果使用现有 `stock.picking` 记录实际执行及库存变化。用户在 Odoo 业务 Order 上手动触发 Ginlong 回传。回传功能读取现有业务数据，不重新开发 WMS 作业，不因回传而执行收货、发货、过账或库存调整。

本提案遵循以下数据来源：

| API | 业务事件 | Odoo 按钮所在业务单据 | Payload 数据来源 |
|---|---|---|---|
| API02 | 收货确认 | 入库 Order | 现有入库订单上的收货数据 |
| API04 | 入库完成 | 入库 Order | 与该订单业务数据匹配的已完成 `stock.picking`、`stock.move.line` |
| API06 | 备货完成 | 出库 Order | 出库订单及本次选择的实际作业记录；实际产品、SN、数量、托盘等优先从关联 `stock.picking`、`stock.move.line` 读取 |
| API08 | 发货完成 | 出库 Order | 与该订单业务数据匹配的实际离仓 `stock.picking`、`stock.move.line` |
| API10 | 盘点完成 | 客户盘点 Order | 关联的仓库实盘结果；不得用盘点订单计划数据替代 |

Order 与 `stock.picking` 不建立强制关系；按现有业务标识和实际数据匹配、核对。多张 picking 时由用户在 Wizard 选择本次回传的实际作业记录。是否逐张或汇总提交仍须服从已确认的 Ginlong 契约。

## 2. 回传 Endpoint 配置

1. CC-003 修订范围新增轻量 Endpoint 配置模型及读取能力。API02/04/06/08/10 各自的 Endpoint URL（含 Ginlong `{objectid}`）和 HTTP Method 由管理员配置，应用代码不写死 objectid 或方法。
2. 缺少、无效或不完整的接口配置时，禁止发送请求，并向用户显示指出接口及缺失配置项的明确提示。
3. CC-003 实现配置数据模型和业务读取；CC-004 再提供管理员菜单及管理界面。菜单/UI 延后不代表可在代码中填入临时默认 objectid 或方法。
4. 配置和 HTTP 客户端复用现有 Odoo/WMS 配置、安全和日志能力；不新增认证框架。Ginlong 当前已提供的接口无鉴权/Key 要求，不额外发送凭据。

## 3. Wizard 与手动发送流程

用户点击相应 Order 的回传按钮后：

1. 系统自动读取当前订单及其已有实际作业/实盘结果，不要求重复录入已有数据。
2. 对多张 picking，Wizard 列出可选的实际作业记录，并由用户选择本次回传范围。
3. Wizard 展示回传范围、关键业务数据和完整 Payload 预览。
4. 仅当 Ginlong 已确认的必填字段确实无法从对应现有记录取得时，才允许补充该缺失值；补充项仅用于本次回传，不复制为第二套业务记录。不得将回传用户或点击时间冒充仓库实际操作人/作业时间。
5. 用户确认后执行一次同步 HTTP 调用，使用合理超时，不自动重试。通过 `worlddepot` 现有 API 日志机制记录请求、响应和错误，页面显示调用结果。
6. 缺少必需实绩数据或配置时禁止发送并明确提示。不得通过计划数据伪造实绩字段，不得因数据缺失而隐式省略 Ginlong 已确认的必填字段。

现有回传日志及普通 Odoo 事务处理继续沿用；不新增 attempt/游标、后台队列、post-commit、独立事务或自动重试机制。

## 4. API10 盘点模型边界及实际检查结果

项目盘点业务按用户确认由两个业务对象组成：**客户盘点订单**和**仓库实盘结果**。API10 必须从实盘结果读取实际采集的 SN、产品及数量，并关联客户盘点订单。盘点计划值与实际采集值须明确区分。

- 不使用 `stock.quant` 推算盘点结果，不访问其当前数量作为 API10 Payload 来源，不执行库存调整。
- 不将客户盘点订单上的目标 SN、计划产品汇总或计划数量冒充实盘数据。
- 优先复用现有客户盘点订单、仓库实盘结果模型及其关联字段；不新增平行盘点订单、结果或 SN 存储模型。
- 操作人和操作时间只读取实盘业务记录中的实际值；缺失时不得用 Odoo 回传用户/点击时间代替现场信息。
- Wizard 不重复录入已有实盘数据。只有 Ginlong 确认必填、且实盘模型确实缺少的数据，才可按其真实来源和用途补充；无可证实来源时阻止发送并记录阻塞。

### 4.1 源码与运行环境核查记录

本次在项目源码和既有 `odooce_karlrapp` 数据库进行了只读 ORM 模型注册/字段检查：

| 检查对象 | 观察到的事实 | 对 API10 的影响 |
|---|---|---|
| 当前 Ginlong addon | 有 `ginlong.stocktake.task`，作为客户盘点任务/订单承载对象，字段包括 `count_order_no`、`owner_code`、`warehouse_code`、`sn_list_json`、`state`，以及指向任务产品行的 `line_ids` | 订单侧字段表达 API05 接收的盘点任务/计划范围，不是实盘结果 |
| 当前任务产品行 | `ginlong.stocktake.task.line` 通过 `task_id` 关联任务，保存 `product_code`、产品名称、规格及计划 `quantity` | 不包含 API10 实际采集结果，不得当成实盘明细 |
| 当前 Odoo ORM 注册模型 | 本次对 `odooce_karlrapp` 的 ORM 模型注册表及 `world.depot.*` 字段检索，没有识别出第二个独立的仓库实盘结果模型或它与客户盘点订单的关联字段 | 提案保留“两模型”业务边界，但技术模型名、关联字段及现场数据字段尚无法由当前 checkout/数据库证据确认；API10 实际取数与完整发送验收保持 BLOCKED，直至模型映射得到源码/ORM证据 |

以上核查没有使用 `stock.quant` 或其数据推算结果。此发现不否定项目确认的“两模型”业务设计；它说明当前检查的源码和数据库注册信息未能定位实盘结果对象。实施前须先在现有 WMS/Gateway 交付中确认真实模型名和关系，再复用该能力；不得用计划任务或创建平行模型绕过缺口。

## 5. 数据口径与来源要求

| 字段类别 | 首选来源 | 约束 |
|---|---|---|
| 产品、SN、数量 | 对应 API 的实际业务执行/实盘记录；API04/06/08 取所选实际 `stock.picking`/`stock.move.line`，API10 取仓库实盘结果 | 不从请求计划量代替实际量 |
| 托盘 | 现有 picking/move line 的实际包裹/托盘关系或实盘结果中的实际托盘字段 | 不依据订单计划数推定实际托盘数 |
| 重量 | 有实际称重记录时取实际值 | 订单 `weight_subtotal` 等计划/订单总值不得冒充执行重量 |
| 实际操作人、操作时间 | 对应实际仓库作业/实盘记录 | picking 负责人、记录创建者/修改者、回传用户和按钮点击时间不得冒充现场操作信息 |
| 订单及货主 | 当前业务 Order 与接口已确认字段 | 不额外创建货主/产品映射或归属校验 |

若现有模型缺少 Ginlong 必填字段，先根据字段来源、记录粒度和业务含义确认可否由用户补录。所有补录必须在 Wizard 中明确标识为人工补充，不得伪装成系统已记录的实际作业数据；Ginlong 未确认其语义的字段仍列为 Open Item。

## 6. 外部契约 Open Items

本次提案只把 endpoint 地址与 HTTP 方法的配置机制定为可配置；没有假定各接口的实际 URL、method、动作值或多次回传语义。

| Open Item | 当前依据/冲突 | 阻塞范围 |
|---|---|---|
| 各回传 API 的实际 `{objectid}` 与 HTTP Method | V3.2 未给出逐接口值；按本提案由管理员配置 | 配置未完成时对应接口禁止发送；本地可测试配置读取和缺失提示 |
| API02/API08 的 action、确认值及撤销语义 | V3.2 字段说明、触发描述与 JSON 示例不一致 | 对应动作的完整 Payload/真实契约验收 |
| API04/API06/API10 的删除/撤销 action 字面值和含义 | V3.2 未提供足够明确的一致请求样例 | 撤销功能验收；不得擅自猜枚举 |
| API04/06/08 多 picking 的提交范围、部分执行及重复调用规则 | V3.2 不能确定逐 picking、累计或订单汇总语义 | 受影响的多 picking/增量场景；单条实际记录的本地映射可独立验证 |
| API06 palletQty、totalWeight 口径及 JSON 数值类型 | V3.2 有计划订单汇总字段，但未确认其是否为实际值；DECIMAL 与字符串示例不一致 | 完整 API06 Payload；不以计划值代替实际值 |
| API04/06/10 必填 operator/operationTime 的来源与粒度 | picking 可提供完成时间和执行明细，但负责人/记录创建者不等于现场操作人；盘点实盘模型尚未定位 | 缺实际人员/时间的对应接口或 SN 记录 |
| API10 仓库实盘结果模型名称、客户盘点订单关联、字段 | 项目确认两模型职责，但当前源码及 `odooce_karlrapp` ORM 注册表未识别结果模型/关系 | API10 的取数、Payload 生成及完整回传验收 |
| API10 部分实盘、重复回传与撤销范围 | V3.2 对分批/撤销的完整语义仍不充分 | API10 增量、重复和撤销场景 |

缺少的契约只阻塞其依赖场景，不影响其他能独立验证的配置、Wizard 数据预览、权限、日志和错误反馈功能；任何尚未执行或依赖未满足的测试均不得记为 PASS。

## 7. 拟修订的范围和验收

获批后，CC-GIN-003 v1.1 只在原范围基础上修订回传功能：

- 新增 endpoint 配置 ORM 模型/读取器；管理员 UI 属于 CC-004。
- 新增位于相应业务 Order 的按钮与回传 Wizard；自动提取数据、选择本次实际作业范围、预览 Payload、补充确实缺少且允许补充的必填项、人工确认并同步发送一次。
- API04/06/08 从现有实际 picking/move line 数据读取；API10 必须复用客户盘点订单与仓库实盘结果，模型/关系未定位前保持阻塞。
- HTTP 调用设置超时、不自动重试；复用 `worlddepot` API 日志，不增加日志框架、回传状态机或事务调度机制。
- 继续执行原 CC-TEST-001–007 的完整性要求，按以下可验证子项分开记录：

| 验收项 | 结果条件 |
|---|---|
| Endpoint 配置 | 每接口分别读取管理员设置的 URL/objectid 与 method；缺配置不发送并有明确提示 |
| 数据自动读取 | API04/06/08 从选择的实际执行记录取值；API10 从实盘结果取值并关联客户盘点单；不得从 `stock.quant` 或计划值生成 API10 实绩 |
| Wizard | 展示本次范围和 Payload；多 picking 可选择；不重复录入已有数据；补充项明确标识并只针对真正缺失的必填字段 |
| 手动调用 | 只有点击并确认后执行一次同步 HTTP；配置缺失、核心实绩缺失或权限不允许时不发送 |
| 日志/结果 | 复用现有日志记录请求、响应/错误；页面反馈错误；超时不自动重试；凭据不写日志 |
| API10 隔离 | 不访问 `stock.quant` 推算结果、不修改库存、不使用客户订单计划数据冒充实盘数据 |

出站调用仍使用 Mock/测试替身自动化；未经另行批准不访问 Ginlong 网络。API10 的模型来源未确认前，相关完整数据验收标为 BLOCKED，不能用只验证 Wizard 框架或计划字段映射替代。
