## 1. 草案目标

为阶段 1 的 Ginlong 入站数据处理准备一个可评审的实施边界：API01、API03、API05、API07 按已批准字段来源接入现有 Odoo WMS / 产品对象；同时将“订单货主不再强制绑定项目货主”和“必须记录托盘生命周期”作为待上游基线纳入的项目要求。

**本草案不构成可执行 CC。** 当前 SRS v1.0 未正式纳入后两项要求，TDD v0.3 也没有批准对应技术设计。必须先完成 SRS/TDD 修订与批准、更新并重新基线化 Implementation Plan，再据实际变化修订并冻结 CC-GIN-002，方可实施受影响内容。

### 2.2 边界

- Odoo 是 Ginlong 与 Karl Rapp 间的数据交换枢纽；`ginlong_apis` 只处理 Ginlong ↔ Odoo。既有 WMS 负责订单作业及库存，`karlrapp_gateway` 负责 Odoo ↔ KR。
- API01/03 只做字段映射并调用现有 WMS 服务，不重复实现仓库收货、发货、拣货、上架或库存业务逻辑。
- API05 盘点模型独立于库存账。禁止访问/读写 `stock.quant`，禁止调用库存调整或过账服务；盘点任务/采集不得改变在库数量。
- API07 不另建 Ginlong 产品档案或映射模型。除明确字段完整性、格式、权限与现有 WMS 主数据规则外，不增加货主-产品归属等新业务校验。
- 不实现 API02/04/06/08/10 人工回传按钮（由后续阶段 CC 覆盖），不实现 API09 库存查询，不实施 `karlrapp_gateway`。

## 3. 上游基线门禁

以下项目未完成前，CC-GIN-002 不得冻结或进入编码：

1. 修订并批准 SRS：明确订单货主可独立于项目货主；明确托盘稳定标识及收货、库内移动/拆装、出库所需追踪事件和验收数据。不要把未经确认的字段/规则塞入 CC。
2. 修订并批准 TDD：明确订单 Owner 字段与项目关系的处理；评估标准 Package / Stock Move 历史是否已覆盖托盘生命周期，只有证据显示不足时才定义最小扩展；不改变 API05/10 与库存账隔离。
3. 更新并重新基线化 Implementation Plan：对齐新的 SRS/TDD 版本、阶段验收和 CC 映射，记录影响分析。
4. 将 API 01/03/05/07 的确认字段和本地模拟边界写入冻结 CC；API03 方向继续标注为 A-003 开发假设，直至 Ginlong 正式确认。
5. 完成 CC 模板来源同步，或由用户另行明确授权在 BLOCKED 状态下冻结；本草案不替代该流程。

Ginlong 完整外部协议缺失不阻塞可依据现有批准字段进行的本地模拟工作；但依赖缺失协议的动作、唯一性、删除/重复/迟到规则、单位和枚举必须保持待决，不得从示例推导为业务契约。

## 5. 现行保持行为与禁止项

- 认证、Token、权限和 API 日志继续复用 `worlddepot`；不建立第二套认证或日志框架。
- 继续屏蔽日志中的 Secret/Token；非凭据业务 Payload 不整体脱敏。
- 不使用、不安装、不启用 `stock_barcode`。
- 不通过 `stock.quant` 实现盘点，不进行库存调整；正常 WMS 收发货仅调用现有业务服务。
- 不建立订单-货主映射表、Ginlong 产品档案或 owner-product 归属规则。
- 不为解决 Ginlong 协议缺失而推断方向、字段单位、删除、幂等或业务状态规则。
- 不把 Owner 解耦或托盘生命周期的技术方案视为已经批准；只能实施经更新 SRS/TDD 确定的方案。
