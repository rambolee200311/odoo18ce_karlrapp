# API02/04/06/08 已成功事件重复回传确认修订提案

**版本：** v0.2（Human Review 批准记录）  
**状态：** APPROVED；已纳入 SRS v1.7、TDD v2.0、Implementation Plan v2.5 及 CC-GIN-010 v1.0  
**范围：** API02、API04、API06、API08 的手动出站回传  
**批准与授权：** 2026-11-25；批准冻结基线并实施 API02/04/06/08 的统一重复回传确认。API10 不变；不访问真实 Ginlong 接口。

## 1. 评审结论

建议统一以规范化当前 Payload 指纹识别历史成功回传。首次回传、当前 Payload 没有成功记录、Payload 已变化及明确失败的请求可直接发送；存在相同 Payload 的成功历史时，由用户确认是否再次发送。结果未知时必须提示“对端可能已处理”，用户确认后才重试。

API02、API04、API06、API08 保持现有业务数据来源、Payload 组织方式和事件粒度。多事件混合处理选项属于可复用的确认能力，不将其写成 API04 专属规则。API10 不在本提案范围。

本提案不修改冻结 SRS/TDD/Implementation Plan/CC。Human Review 批准后，再办理必要的上游基线变更和实施授权。

## 2. 现有实现审查

### 2.1 可复用组件及记录

- `ginlong.api.idempotency` 已保存接口、方向、业务键、事件键、Payload 指纹、状态、尝试次数和响应结果，是现有 API Event/幂等事件记录；没有独立的 `ginlong.api.event` 模型。
- `world.depot.api.log` 保存实际请求、响应、HTTP 状态、错误、请求时间及来源业务记录。
- API02/04/06/08 已有真实业务单据上的回传按钮和现有回传结果反馈。
- 一次性选择和确认适合由通用 `TransientModel` 向导承载；该向导不保存或替代持久化业务事实。
- 入库订单、出库订单使用 `mail.thread`；业务记录 Chatter 可记录用户确认/取消决定。API04 可将操作决定记录到对应入库订单 Chatter，并在消息中列出 Picking。

### 2.2 业务来源、Payload 与事件粒度

| API | 实际数据来源 | 当前 Payload 组织方式 | 当前独立回传事件单位 |
|---|---|---|---|
| API02 | 当前 `inbound.order.status`；`planning→N`，`arrive/inbound→Y` | 一张入库订单生成一个 Payload：`inboundOrderNo`、`action`、`receiptConfirmed` | 一张订单的一个状态 Payload 事件 |
| API04 | 当前入库订单关联的 Done/Incoming `stock.picking` 及其实际 `stock.move.line` | 每张 Picking 独立生成 Payload；`snList` 取该 Picking 实际 move line | 每张 Picking 一个独立事件；一次按钮点击可扫描多张 Picking |
| API06 | 出库订单上已选的 Picking、其实际 move line，以及订单级托盘/重量汇总 | 所有已选 Picking 的 move line 合并进一个订单级 `snList`，同时回传订单级 `palletQty`、`totalWeight` | 当前为一个出库订单级聚合事件；多张 Picking 不等于多个独立事件 |
| API08 | 当前出库订单保存的发货明细状态 | 将明细 `shipment_status` 汇总成一个 `shipmentConfirmed`，连同订单号和 Action 组成单一 Payload | 一张出库订单的一个状态 Payload 事件 |

因此，多 Picking 操作中的“混合成功/未成功事件”当前只会出现在 API04 的多 Picking 扫描中。API06 可能聚合多个 Picking 数据，但该集合对应一个 Payload 和一个订单级事件；不得在本次确认机制中拆成逐 Picking 事件。若未来业务要求改变事件粒度，应另行评审。

### 2.3 当前机制与新要求的差异

| 位置 | 当前行为 | 影响 |
|---|---|---|
| `idempotency_rules.json` API02/06/08 | 事件版本包含来源 `write_date` | 无关单据修改可能改变事件身份；不符合按当前 Payload 判重 |
| `idempotency_rules.json` API04 | 使用 `date_done`，不包含 Payload 指纹，并启用 `skip_successful_event` | 成功 Picking 静默跳过，不能询问用户是否重发 |
| `idempotency.execute()` | 命中同一成功事件时返回历史缓存结果 | 用户无法区分本次发送和历史结果，未真正发出 HTTP |
| `idempotency._run_once()` | 在当前请求事务中写入 `processing`，执行 HTTP 后再写终态 | 唯一约束可阻止同一事件并发执行两次；但未提交的 `processing` 行对其他标签页/Worker 不可见，竞争请求可能等待后拿到完成结果 |
| `send_callback()` | 部分缓存成功路径仍会追加 API Log | 可能出现没有真实 HTTP 请求却新增成功状态日志 |
| `_send_api04_pickings()` | 已成功 Picking 直接跳过；失败/未知项继续处理 | 没有统一选择“仅未成功/全部/取消”的多事件交互 |

现有测试 `test_outbound_http_failure_retries_same_event_then_caches_success` 中，接收端收到两次 HTTP，第三次按钮调用复用成功缓存，但 API Log 有三条。新契约必须将 HTTP 次数、Event 和 Log 分开断言，不得把缓存命中写成一次真实发送。

审查位置：

- `mymodules/ginlong_apis/idempotency.py`：`_outbound_event_key()`、`execute()`
- `mymodules/ginlong_apis/data/idempotency_rules.json`：API02/04/06/08 事件配置
- `mymodules/ginlong_apis/models/ginlong_callbacks.py`：Payload 构造、`send_callback()`、`_send_api04_pickings()`
- `mymodules/ginlong_apis/models/api_control.py`：幂等事件模型与唯一约束
- `mymodules/ginlong_apis/models/api_log.py`：来源单据、接口编号和业务键日志关联
- `mymodules/ginlong_apis/tests/test_ginlong_api.py`：当前出站重试/缓存测试

## 3. 建议的最小行为

### 3.1 Payload 判重

1. 从已保存 ORM 记录生成并校验本次 Payload，再计算规范化 Payload 指纹。
2. 成功历史匹配按 API、方向、来源业务记录身份、Action 和当前 Payload 指纹执行；API04 的来源记录为 Picking，其余三个接口的来源记录为业务订单。
3. 不使用订单或 Picking 的 `write_date` 判断业务事实是否变化。实际业务状态或数据只在改变了 Payload 后，才形成新的 Payload 事件。API04 的 `date_done` 仍作为规定的 Payload 数据来源，不单独决定是否重复。
4. 明确失败的同指纹请求直接允许人工重试。结果未知不是明确失败，必须先提示远端可能已经处理，再由用户确认是否重试。

### 3.2 通用确认向导与选择

使用同一个通用 `TransientModel` 确认向导，展示本次回传对象、来源单据/Picking、上次成功时间、返回状态及安全结果摘要。界面不展示可编辑 JSON。

- **单个事件命中成功历史：** 显示确认重复发送或取消。确认后实际重发当前 Payload；取消不发送。
- **多个独立事件同时处理且成功与未成功项混合：** 显示三个选项：
  1. **仅回传未成功项（默认）**：跳过成功项，发送首次项及明确失败项。结果未知项单独提示可能已被对端处理；未经用户确认不发送该项。
  2. **回传全部**：包括成功项并重新发送；结果未知项仍须明确确认风险。
  3. **取消**：本次不发送任何请求。
- **结果未知项：** 无论是否存在成功项，均显示可能重复处理的风险。用户明确确认后才发送该未知事件；其他安全可发送项可按所选范围处理。
- 不同接口继续按现有事件粒度组织操作。API04 的一次向导可列出多个 Picking 事件；API06 一个聚合 Payload 仍然只有一个事件，不拆分成按 Picking 的选择。

### 3.3 防重复点击与并发执行

1. 回传按钮和向导确认按钮在各自 RPC 执行期间进入禁用/加载状态；请求成功或失败返回后恢复。禁用状态只改善当前页面交互，不能代替服务端幂等控制。
2. 同一 API、来源、Action 和 Payload 指纹使用现有 `ginlong.api.idempotency` 唯一键及执行器原子占位；同一事件同时最多有一个执行器可以调用 HTTP。不得引入独立的防抖/锁服务。
3. 若事件已处于 `processing`，直接返回“正在处理”提示；不发送 HTTP，也不弹历史成功确认框。多事件操作中，处理中项报告为忙碌并跳过，其他符合所选范围的事件仍按规则处理。
4. 当前 `_run_once()` 在同一请求事务中写入 `processing`，竞争事务看不到未提交行，会等待唯一键冲突后才读取完成结果。为区分“点击时已有历史成功”与“本次请求等待期间刚完成”，最小扩展需向幂等执行器传递本次请求开始时间，并返回执行来源/重叠结果。若竞争事件在本次点击后才完成，第二请求应返回“该事件刚完成/此前正在处理”，不得弹历史成功确认框；用户之后再次点击时，才按历史成功事件显示确认框。该时间只用于并发请求分类，不用于业务事实或 Payload 身份判定。
5. 用户确认令牌参与重复发送 Event identity，确认按钮第一次执行后即消费。重复点击或多标签页重放同一令牌时复用该确认事件结果但不再调用 HTTP、不新增 Event/API Log；UI 同时将确认按钮置为处理中。

### 3.4 确认有效性及 Payload 新鲜度

- 向导只保存来源记录引用、API 编号、当前 Payload 指纹、待处理事件范围及确认令牌，不保存 Payload 业务事实。
- 用户确认时重新从 ORM 生成并校验 Payload。若指纹已变化，放弃旧确认，按新 Payload 重新判重。
- 用户取消不发送；确认和取消均通过来源业务记录现有 Chatter 追加 API、范围、决定、用户及时间。

### 3.5 Event、Log 与历史兼容

- 复用 `ginlong.api.idempotency` 保存首次事件、重试状态和经用户确认的重复事件；确认重发创建独立 Event，关联原成功 Event，记录确认用户和时间，原记录不修改。
- 每次实际 HTTP 请求追加一条 `world.depot.api.log`，将其关联来源记录及对应 Event；没有实际 HTTP 请求不得记录成 HTTP 成功。
- 命中历史成功后弹框或用户取消，不新增 HTTP API Log；Chatter 保存决定记录。失败和未知的每次实际尝试分别追加 API Log。
- **历史数据兼容建议：** 不重写或删除旧幂等行。新判重先查新格式 Event；旧成功记录无法可靠按新算法重建来源身份时，以 `world.depot.api.log` 的 `ginlong_api_code`、`source_record`、解析后的 `request_data` 指纹和 `success=True` 做兼容查找。旧代码可能为缓存响应追加成功 Log；若同源同 Payload 有多条成功 Log，使用最早成功 Log 作为原成功证据/时间，避免把后续缓存回放当作真实新发送。新 Event/Log 增加必要的关联字段，使后续历史可直接追溯。

## 4. REP 测试契约

所有测试通过真实 Odoo 回传按钮入口和本地 Mock HTTP 接收端执行。分别按 API02、API04、API06、API08 统计，断言实际 HTTP 次数及 Payload、Event 行、API Log 和 Chatter。

| ID | 场景 | 预期行为与断言 |
|---|---|---|
| REP-01 | 无历史成功的首次回传 | 直接发送一次；创建成功 Event 和一条真实 HTTP Log |
| REP-02 | 当前 Payload 与历史成功 Payload 不同 | 不显示重复确认，直接发送；旧 Event/Log 保留，新 Payload 有独立记录 |
| REP-03 | 同一成功 Payload 再点回传 | 显示最近成功时间、状态、结果；用户决定前 HTTP 次数不变 |
| REP-04 | REP-03 选择取消 | HTTP 次数不变；不新增 HTTP Log/Event；Chatter 记录取消用户、时间和范围 |
| REP-05 | REP-03 确认重复回传 | Mock 收到相同 Payload 的新 POST；新增独立 Event 并关联旧 Event；新 Log 只记录实际请求；确认人/时间可追溯 |
| REP-06 | API02 `receiptConfirmed=N` 已成功，业务状态映射成 `Y` | 新 Payload 直接发送；不得仅因同订单号弹重复确认 |
| REP-07 | 同 Payload 的业务记录发生无关修改，导致 `write_date` 变化 | 仍识别为同一成功 Payload 并提示确认；重复判定不受 `write_date` 影响 |
| REP-08 | 明确失败后再次点击 | 不提示“成功重复”；直接重试；每次实际 HTTP 各追加 Log，失败历史保留 |
| REP-09 | 请求结果未知 | 对可能已处理风险显示确认；取消不发，确认后真实重试；保留未知历史及本次尝试 Log |
| REP-10 | 用户打开向导后、确认前业务 Payload 改变 | 确认时重读 ORM；不发送旧 Payload，按新指纹重判 |
| REP-11 | 同一向导确认按钮双击/并发提交 | 同一确认令牌最多造成一次 HTTP 发送；不能产生重复 Event/成功 Log |
| REP-12 | 历史旧格式成功事件 | 以旧 API Log 的来源、API、规范化报文指纹和成功状态识别；不因 `write_date`/事件键格式变化误发 |
| REP-13 | API04 多 Picking：成功与失败/首次事件混合 | 默认“仅回传未成功项”只发首次/失败项；成功项跳过；未知项须确认 |
| REP-14 | API04 多 Picking 选择“回传全部” | 用户确认后逐 Picking 发送成功事件；每张 Picking 各自有 Event/Log；Payload 仍按原规则生成 |
| REP-15 | API04 多 Picking 选择“取消” | 本次没有任何 HTTP；Chatter 记录取消范围 |
| REP-16 | API06 多 Picking 聚合 Payload | 多个已选 Picking 的明细仍合成一个订单级 Payload/Event；相同聚合 Payload 成功后确认重复；选择集合/数据变化导致 Payload 变化时直接发送 |
| REP-17 | API08 单订单确认 Payload 重复 | 同指纹成功时弹确认；确认才实际重发，取消不发；不拆成 Picking 事件 |
| REP-18 | 同一页面连续点击回传按钮，Mock 延迟响应 | 第一次 RPC 执行期间按钮禁用；Mock 只收到一次 HTTP；完成后按钮恢复 |
| REP-19 | 两个浏览器标签页/会话同时触发同一事件 | 现有幂等占位只允许一个 HTTP 执行；竞争请求提示处理中/刚完成，不发送第二次、不弹历史成功确认框；API Log 只对应真实 HTTP |
| REP-20 | API04 多 Picking 中一项处理中，其他项首次/失败 | 处理中 Picking 不重发、不弹历史成功框；其他合格项按所选范围发送；逐项断言 HTTP 数量和日志 |
| REP-21 | 同一确认向导连续点击确认，或两个标签页提交同一确认令牌 | 确认令牌只消费一次；Mock 新增且仅新增一次 HTTP；只创建一个重复 Event 和一条对应 API Log，第二次返回已处理提示 |
| REP-22 | 同一事件请求与上次成功完成之间有并发重叠；随后用户再点一次 | 重叠请求不弹历史成功框；重叠完成后新的独立点击才弹重复确认框 |

必须为 API02、04、06、08 各自提供首次、成功重复确认/取消、Payload 改变、明确失败、结果未知及历史兼容的行为证据。API04/API06 的多 Picking 场景按上表实际事件粒度分别测试。

## 5. 最小实施边界

1. 一个共享确认向导与一个通用出站事件预检/分类入口；不为每个 API 单独造确认框或幂等机制。
2. 复用现有幂等与日志模型。只新增支持来源/历史事件关联、重复确认用户/时间、一次性确认令牌和 API Log—Event 关系所必需的字段；不新增独立 Event 模型。
3. 复用现有唯一约束和原子占位保证单一事件单执行；增加执行来源/并发重叠结果识别，使处理中竞争请求不误入历史成功确认流程。界面禁用仅作为辅助。
4. 改用“稳定来源身份 + Action + 规范化 Payload 指纹”识别相同成功事件；移除业务变化判定对 `write_date` 的依赖。API04 打开 Payload 指纹并取消成功事件静默跳过。
5. 将未成功项范围计算作为通用事件批处理能力；保持 API04 每 Picking 一事件、API06 多 Picking 合一订单事件、API02/API08 订单级事件。
6. 只在实际 HTTP 请求后写 HTTP API Log。处理用户决定时写 Chatter；取消不得生成伪造的 HTTP 成功记录。
7. Endpoint、认证、字段校验、Payload 字段、Action、业务来源、Picking 选择/组织方式及 API10 行为保持现有规则。
